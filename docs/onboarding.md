# 首次初始化与部署引导

本文件是 AI 工具在新机器首次打开本仓库时的交互脚本。目标是从“没有本机档案”走到“各工具入口已部署并验收”，由 AI 负责解释、只读探测、生成候选和逐项确认，用户只补充无法探测的信息并做写入授权。

根目录 `AGENTS.md` 是硬约束，本文件是执行细节；两者冲突时以 `AGENTS.md` 为准。首次初始化时 `aiwb` 技能尚未部署，不要等待它被自动发现。

## 开始前先读

按顺序阅读，不需要通读整个仓库：

1. `AGENTS.md`：修改边界、安全门禁和验证要求。
2. 本文件：待办清单、交互脚本、部署后指导。
3. `README.md` 的“快速开始”和“安全边界”：命令入口与写入范围。
4. `docs/maintenance.md` 的“首次初始化”“部署执行与回滚”“冲突与漂移”：失败处理和后续维护。
5. `docs/adapters.md` 与 `adapters/targets.json`：各工具配置根、入口、技能目录、版本探测方式和证据状态。
6. `machines/_template.md`：候选档案的骨架。
7. 用户追问设计原因时再读 `docs/design.md`；初始化阶段不要为了“了解全貌”通读规则正文。

只读盘点限于上述文件、本机工具配置目录的存在性与版本探测文件。不要全盘扫描，不要读取用户规则正文、记忆、对话记录、账号内容或与本次初始化无关的目录。

## 用户需要知道的基本知识

开场先用简短条目讲清以下内容，再开始盘点。用户表示已经了解时可以压缩，但不能省略写入范围和确认门禁。

- **仓库、档案、入口是三样东西**：仓库保存可复用的规则与技能；`machines/<主机名>.md` 保存本机路径、工具启用与版本要求，只在本机存在、不入库；各 AI 工具的入口文件由 `build` 生成、由 `deploy` 写入带标记的块或独立文件。
- **命令的读写边界**：`build` 只生成 `dist/`；`detect`、`deploy --dry-run`、`status`、`doctor` 只读；执行部署（CLI 的 `deploy --apply` 或 GUI 的“执行部署”）才会写工具入口、全局工作台目录和技能 junction。预演不是执行。
- **写入范围与保护**：只写各工具入口的工作台块或工作台创建的文件、全局工作台目录、指向本仓库的技能 junction；不改用户原有内容，不接管工具自带规则、技能、插件和人设。WorkBuddy 用户级写入账号记忆目录下的 `MEMORY.md`：目录名由配置根中的账号快照动态解析，不写死用户标识；区块外记忆保持原样，内容超预算时另写拆分文件。每次写入前备份，原子替换，写后校验，失败回滚。
- **部署方式由你选择**：初始化完成后，AI 会让你选择 CLI 或 GUI。两者共用同一套核心、备份与校验；CLI 由 AI 预演并经你确认后执行，GUI 由你在部署页预演、勾选确认并执行，AI 不代替你点击。不要默认只提供 CLI 一条路。
- **版本要求是可选的核对条件**：留空表示不核对。填写后，部署预演与执行、合并、备份恢复和技能 junction 会先核对实际版本；不符或检测不到时部署跳过该目标、合并与恢复阻止，卸载不受影响。首次初始化默认全部留空，不照抄其他机器。
- **首次部署前技能不可用**：`aiwb` 技能要等首次部署执行、创建 junction 后才出现在支持技能的工具中，所以本次由 `AGENTS.md` 和本文件引导；部署后用新会话验证技能是否可见。
- **隐私**：机器档案包含本机路径和主机名，不能提交；仓库文档和 `content/` 只写占位符。AI 不把机器档案正文、环境变量值或账号信息写入仓库。

## 待办清单

开场时把清单和初始状态展示给用户，之后每完成一项就更新。状态用“待开始 / 进行中 / 待确认 / 已完成 / 受阻 / 跳过”，受阻时写明原因和需要用户提供的信息。

| 编号 | 事项 | 完成标准 |
|---|---|---|
| 0 | 讲解基本知识与写入范围 | 用户知道将读写什么、哪些操作需要确认 |
| 1 | 只读盘点 | 主机名、运行时、工具目录与版本探测结果都有依据 |
| 2 | 生成候选档案 | 草稿展示给用户，占位符和示例行已处理 |
| 3 | 逐项确认 | 每个写入项都有“已确认 / 留空 / 跳过”的结论 |
| 4 | 写入并校验 | 档案已创建，`settings show --json` 无问题，`build` 通过 |
| 5 | 选择部署方式 | 用户明确选择 CLI 或 GUI，并知道两种方式共用同一核心 |
| 6 | 复核部署预演 | 用户看过入口动作、冲突、版本阻止与跳过项 |
| 7 | 首次部署 | 按所选方式执行：CLI 由 AI 在确认后 `--apply`，GUI 由用户在页面勾选确认；`status`、`doctor` 通过 |
| 8 | 验收与后续指导 | 用户知道如何用新会话验证、如何继续维护 |

## 1. 开场

开场回复包含四部分，避免直接抛命令或让用户自己填表：

1. 本次目标：创建本机档案并完成首次部署。
2. 基本知识与写入范围：按上一节压缩成一屏能读完的条目。
3. 待办清单：展示 0-8 项和当前状态。
4. 下一步请求：请用户选择“开始只读盘点”“先解释某一部分”或“暂停”。

优先使用当前 AI 工具的结构化提问；没有时用编号问题等待回复。不要在没有得到开始指令时读取工具目录。

## 2. 只读盘点

按注册表逐项检查，不要凭记忆写路径：

- 主机名：取 `os.hostname()`（PowerShell 可用 `$env:COMPUTERNAME`），必须与将来文件名和 frontmatter 的 `host` 一致。
- 运行时：Node.js、npm、Git 的版本与可执行文件位置；版本不满足 `package.json` 时先说明影响。
- 工具：读取 `adapters/targets.json` 的配置根、入口、备选入口、技能目录和 `versionProbe`，检查目录与文件是否存在；版本值直接按 `versionProbe` 读取，此阶段还没有机器档案，不依赖 `detect`。
- 证据：每项记录“检测到的值 / 依据（文件或命令）/ 是否确定”。“路径存在”不等于“该工具支持用户级入口”，证据强度按 `docs/adapters.md` 和注册表标注，不把推断写成事实。
- 项目：只读取用户确认过的“项目父级”一层，或读取用户主动提供的路径；不做全盘搜索，不递归读取项目内容。

盘点结果用表格回复：`项目 | 检测值 | 依据 | 状态`。检测不到时写“未检测到”，不要猜默认路径。

## 3. 生成候选档案

以 `machines/_template.md` 为骨架，生成 `machines/<主机名>.md` 草稿：

- 替换 frontmatter 与标题中的 `REPLACE_ME`，删除示例项目行；没有项目时保留空表。
- 必须填“项目父级”和“全局工作台”，否则 `build` 无法完成。其余路径按用户实际目录填写或留空，不虚构。
- 已安装工具、版本、入口存在性写入候选并注明依据；无法探测的路径、工具启用取舍和资料目录由用户确认。
- 工具覆盖只在确有需要时填写；自定义工具必须先得到用户的名称、配置根和入口，不能只凭目录猜测。
- 所有版本要求默认留空；不要照抄其他机器的版本，也不要把 `ai-env-clone` 等外部工具的版本写成默认要求。
- 草稿只在回复中展示，不写入文件；同时说明哪些项是自动探测、哪些项必须由用户确认。

档案格式可参考模板的“机器环境”“路径”“项目清单”“设置”“本机特有注意事项”各节。写入前不要展示或保存任何密钥、令牌和账号凭据。

## 4. 逐项确认

按组确认，避免一次抛出几十个字段：

1. **身份与环境**：主机名、系统、Shell、Node/npm/Git 版本。
2. **路径**：项目父级、全局工作台、工作台仓库、各类资料目录、桌面交付目录。
3. **工具**：已安装工具、是否启用、配置根、入口、技能目录、检测到的版本、可选版本要求。
4. **项目与扩展**：项目清单、自定义工具、本机特有注意事项。

用表格列出 `项目 | 候选值 | 依据 | 请确认`，或使用结构化提问。用户确认“其余都对”时，把剩余项逐项标为已确认；用户只确认一部分时，其余项留空或跳过，并说明影响：

- 缺“项目父级”或“全局工作台”：`build` 会失败，不能进入部署。
- 某个工具路径未确认：该工具暂不启用或留空，不影响其他目标。
- 版本要求未确认：保持留空，之后可用 `settings set` 或 GUI 补充。

不确定的项给出可选项和影响，不替用户拍板，不用 `--force` 跳过校验。

## 5. 写入并校验

用户确认后，由 AI 直接创建 `machines/<主机名>.md`，不要让用户手工复制模板或逐项填写：

1. 若档案已存在，只展示差异；用 `settings` 修改，不覆盖其他主机档案，不整文件重写。
2. 不提交机器档案，不把其内容写进仓库文档。
3. 运行 `node src/cli/main.mjs settings show --json`，要求 `available`、`writable` 为真且 `issues` 为空；有问题先修正档案，不要强行继续。
4. 运行 `node src/cli/main.mjs build`，确认构建成功。
5. 运行 `node src/cli/main.mjs detect --json`，复核工具、入口、技能目录与版本检测结果；与盘点阶段不一致时说明原因。
6. 完成 `build` 与 `detect --json` 后进入部署方式选择；不要直接执行 `deploy --apply`。

把结果压缩成表格：构建是否通过、检测到的工具与版本与盘点阶段是否一致。检测或构建失败时停在当前步骤，先修复再继续。

## 6. 选择部署方式

档案、`build` 和 `detect` 都通过后，先让用户选择部署方式，不要默认直接走 CLI：

- **CLI**：AI 运行 `node src/cli/main.mjs deploy --dry-run`（或 `launchers\aiwb.cmd deploy --dry-run`），把计划交给用户复核；用户确认后由 AI 执行 `deploy --apply`。适合希望 AI 逐项解释、在终端完成操作的场景。
- **GUI**：按 7.2 启动本地页面，由用户在“部署”页完成预演、核对、勾选确认和执行。适合希望自己看页面表格并亲自点确认的场景。AI 只提供启动指导和结果解释，不代替用户点击，也不直接调用写接口。
- 两者调用同一套核心，写入范围、备份、版本核对和回滚一致；不存在“GUI 更安全”或“CLI 更完整”的差别。不要替用户默认选 CLI，说明差异后请用户决定，并允许“暂停”。
- 只想部署部分工具时，CLI 用 `deploy --tool <工具 id>`，GUI 在“目标工具”下拉中选单个工具。

用结构化提问请用户选择“CLI / GUI / 暂停”；用户不选时再次询问，不直接开始执行。

## 7. 复核部署预演

### 7.1 CLI 方式

运行 `node src/cli/main.mjs deploy --dry-run`（也可用 `launchers\aiwb.cmd deploy --dry-run`）。预演只读，不会写文件。向用户逐类解释：

- 会写入哪些工具的哪个入口，是新建、追加工作台块还是更新块。WorkBuddy 从配置根的账号快照解析出 `user-<uid>-<作用域>/MEMORY.md` 并向顶部插入带标记区块；快照缺失、无效或过期时解析回落到设备根但部署按需人工阻止，不会写入设备根（配置根下已有账号目录视为疑似已登出，否则视为未检测到已登录账号），预演会显示入口路径提示和当前实际入口。区块与既有记忆合计超过目标线时只留钩子，正文写入 `<配置根>/memory/ai-workbench-global-rules.md`，合计超过注入上限时给出警告。合计按含空白字符计算，并附不含空白字符、文件字节与字数估算，便于和编辑器对照。
- 是否会创建全局工作台目录、脚本 junction 和技能 junction。
- 哪些目标因版本要求未通过而跳过，哪些因冲突或缺少路径需要人工处理。
- 哪些目标被用户停用或未安装，因此不会处理。

请用户明确选择“执行部署”“只部署部分工具”或“暂停”。只部署部分工具时改为 `deploy --tool <工具 id> --dry-run`，并在之后说明未部署的目标。

### 7.2 GUI 方式

可由用户自己运行，也可由 AI 启动；启动命令：

```powershell
node src/cli/main.mjs gui --open
# 或
launchers\aiwb-gui.cmd
```

启动后浏览器会打开带 `token` 的本地地址。地址只在本机使用，不要转发；换端口或重启后旧地址失效。然后按以下步骤指导用户：

1. 打开“部署”页，确认页面说明的写入范围。
2. 在“目标工具”下拉中选择“全部”或单个工具。
3. 点“预演”；页面列出将新建、追加或更新的入口，以及需人工项、版本阻止与跳过项。WorkBuddy 另有“记忆注入”表，显示模式（内联/钩子）、区块字符数、全文合计/上限、不含空白字符、文件字节、字数估算与拆分文件。这一步不写文件。
4. 逐项核对；有冲突或需人工处理项时先停下说明，不要勾选确认。
5. 确认无误后由用户自己勾选“我已核对预演结果，确认写入外部入口与全局工作台”。勾选后“执行部署”才会启用，AI 不代替勾选或点击。
6. 用户决定暂停时关闭页面即可，预演不会留下外部写入。

AI 可以解释页面结果和指出风险，但不要直接调用 `/api/run` 或任何写接口绕过页面确认。

## 8. 首次部署

### 8.1 CLI 方式

只有用户看清预演并明确确认后，才运行 `node src/cli/main.mjs deploy --apply`（也可用 `launchers\aiwb.cmd deploy --apply`）；部分部署加 `--tool <工具 id>`。不要自动执行，也不要用 `--force` 掩盖冲突。

执行后：

1. 报告每个目标的动作、备份位置和结果；失败时说明已成功写入的目标、回滚情况和剩余目标。
2. 运行 `node src/cli/main.mjs status`，确认入口状态与技能 junction。
3. 运行 `node src/cli/main.mjs doctor`，确认体检通过；有未通过项时按输出修复，不跳过。
4. 提醒用户用各工具的新会话验证入口加载和 `aiwb` 技能是否可见；部分工具需要重启或重新打开工作区。WorkBuddy 还要开新会话问“当前生效的自定义指令有哪些”，能复述工作台规则才算记忆注入成功。

### 8.2 GUI 方式

只有用户自己在页面勾选确认并点击“执行部署”后，才表示部署被授权。AI 不代替用户点击，也不在后台直接调用写接口。

执行后：

1. 请用户把页面结果（每个目标的动作、失败项与备份提示）告诉你，或由 AI 运行 `status`、`doctor` 复核；页面“总览”（含体检结果）也可刷新查看。
2. 失败或出现冲突时，按页面提示和 `docs/maintenance.md` 的“冲突与漂移”处理，不静默重试，不要求用户用 `--force` 绕过。
3. 如果用户在预演后关闭页面或没有点击执行，不能假定部署已发生；重新预演后再决定。
4. 部署成功后，提醒用户用各工具的新会话验证入口加载和 `aiwb` 技能是否可见。WorkBuddy 需另开新会话问“当前生效的自定义指令有哪些”，能复述工作台规则才算注入成功。

## 9. 验收与后续指导

验收后给用户一份“现在能做什么”的简短清单，并指向对应文档，不要把命令全量倒出：

- **验证**：新会话中确认规则入口已加载、`aiwb` 技能可被发现；未加载时先查工具设置和入口路径，不假定规则已生效。WorkBuddy 用新会话问“当前生效的自定义指令有哪些”，能复述才算注入成功；只看到 `MEMORY.md` 里有区块不算。
- **日常修改**：改通用规则或技能 → `content lint` → `build` → 按偏好用 `deploy --dry-run` 加 `deploy --apply`，或在 GUI 部署页预演并勾选确认 → `status`、`doctor`。详见 `docs/maintenance.md`。
- **启动方式（按个人习惯）**：CLI 用 `launchers\aiwb.cmd <命令>` 或 `node src/cli/main.mjs <命令>`；GUI 用 `launchers\aiwb-gui.cmd`（可双击或建快捷方式）或 `node src/cli/main.mjs gui --open`。两个启动器都只是 Node 命令的薄包装，写入范围与确认门禁一致。
- **图形界面**：总览、部署、合并、项目、内容、设置、备份、历史、诊断都在本地页面；写入动作需要页面勾选确认。
- **回滚与冲突**：`backup list` 找到备份 → `backup restore` 预演 → 确认后 `--apply`；入口被手改时用 `merge` 或 GUI 合并页处理，不手工覆盖。详见 `docs/maintenance.md` 的“冲突与漂移”。
- **版本要求与自定义工具**：`settings show` 查看 → `settings set` 预演 → 确认后 `--apply`；内置工具与自定义工具都可选填版本要求，留空表示不核对。
- **项目挂载**：`scan` 查看 → `attach <项目路径>` 预演 → 确认后 `--apply`；已跟踪入口默认阻止，按需选择 `local` 或 `append`。
- **卸载**：`uninstall` 预演 → 确认后 `--apply`；保留全局工作台目录、用户内容和备份。
- **下次初始化**：部署后 `aiwb` 技能可用，后续维护优先由技能接管；本文件保留为首次初始化的完整说明。

最后把待办清单更新为完成，列出仍可选择跳过的项（例如尚未挂载项目、暂未填写版本要求），并询问用户是否需要继续。

## 失败与例外

- **档案已存在但内容不完整**：展示差异并补齐必填项，不整文件覆盖。
- **主机名不一致**：以本机实际主机名为准，先确认是否重命名档案；不要同时保留两个本机档案。
- **工具未安装或路径不存在**：标记为未安装或停用，不创建猜测路径；用户明确要接入时再登记自定义工具。
- **版本检测不到**：保持版本要求留空；先确认安装根目录，必要时在 `## 设置` 的 `env` 中定义 `AIWB_*_HOME` 后重试。
- **预演出现人工处理项**：停在预演阶段，说明原因和可选处理方式，不执行 `--force`。
- **WorkBuddy 记忆注入超预算**：超过目标线会自动改为钩子加拆分文件；超过注入上限时仍可置顶写入但会提示部分内容可能不进入会话。不要手工删除拆分文件或改写标记，先调整 `content/rules/` 后重新部署。
- **WorkBuddy 快照无效时部署被阻止**：预演或设置页出现入口路径提示时，说明账号快照缺失、无效、超过 4096 字节或超过 30 天，或其中的用户/企业标识不能作为目录名；工作台不会写入设备根，先启动 WorkBuddy 登录刷新快照，再重新预演。不要为绕过提示硬编码账号目录，确认要固定入口时才用 `tools.workbuddy.entryPath` 覆盖。
- **GUI 无法启动或页面打不开**：检查命令输出、端口占用和带 `token` 的地址；不要直接调用写接口绕过确认，可改回 CLI 方式并重新征求用户同意。
- **用户拒绝写入或部署**：停止并保留候选草稿，把待办标为“受阻”或“跳过”，不要反复催促。
- **用户要求读取私人内容**：只读取与本机档案直接相关的路径和版本文件；涉及规则、记忆、对话或账号内容时先说明用途并取得许可。
