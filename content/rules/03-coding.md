# 编码、注释与提交规范

## 代码质量

- 命名要表达意图；优先可读性，不为缩短代码牺牲清晰度。
- 保持最小改动，不顺手重构无关代码，不引入当前任务不需要的抽象或配置。
- 优先复用现有实现和项目约定；新增依赖前说明必要性、体积和维护成本。
- 不留下半成品、调试输出、注释掉的旧代码和临时开关。
- 不添加无法触发的兜底分支；只在系统边界校验输入，内部调用信任约定。

## 注释

- 注释使用中文；标识符、命令、路径、错误信息保持原文。
- 只写必要注释，解释“为什么”和约束，不复述代码已经表达的“做什么”。
- 函数注释写清四要素：说明、参数、返回值、必要逻辑或注意事项。
- 不随意删除旧注释；注释与代码不一致时更新注释，确需删除要说明理由。
- 不写会话过程、任务编号、测试统计或“本次修改”之类会过期的注释。

各语言建议格式：

| 语言 | 格式 |
|---|---|
| C# | XML 文档注释：`<summary>`、`<param>`、`<returns>`、`<remarks>` |
| C/C++ | Doxygen：`@brief`、`@param`、`@return`、`@note` |
| Python | docstring：摘要、Args、Returns、Raises、Notes |
| JavaScript/TypeScript | JSDoc：`@param`、`@returns`、`@remarks` |
| SQL | `--` 行注释；必要处说明参数与结果 |

## 安全与健壮性

- 不引入命令注入、SQL 注入、XSS、路径穿越、不安全的反序列化等常见漏洞。
- 外部输入在系统边界校验；路径、命令参数和查询条件必须按目标环境正确转义或参数化。
- 不硬编码密钥、令牌、密码和账号凭据；使用环境变量或受保护的配置。
- 错误处理只覆盖真实可能发生的失败；失败信息要能定位问题，不吞异常。
- 写文件优先使用临时文件加原子替换；涉及用户数据的操作要可回滚。

## 提交说明

- 使用中文，写清改动目的和影响，不写实现流水账。
- 一个提交聚焦一件事；不把无关修改混进同一提交。
- 按变更单元组织提交，不按操作步骤拆分；同一目标的后续修补、文档和测试同步并入同一提交。历史用于回退和变更记录，不充当撤销列表。
- 不写“修复 bug”这类无法定位问题的空泛说明。
- 不在提交说明中写会话内容、批次号、探针过程或测试统计。
