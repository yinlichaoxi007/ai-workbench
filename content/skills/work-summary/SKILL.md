# 个人工作梳理

## 何时使用

- 用户要求梳理或记录"某段时间干了哪些工作"、按日期或方面汇总工作内容。
- 用户为周报、月报、计划总结准备个人工作素材。
- 用户点名"也包括所有的工作树""只梳理我的""把文档里的工作也算上"这类口径时，按下文默认值执行，不再逐项追问。

## 先读

1. 机器档案 `machines/<主机名>.md`：取"我的名字"作为默认 git 作者，取"项目父级""项目清单"用于跨仓库范围，取"工作计划总结""桌面交付""工作参考资料""全局工作台"作为文档来源路径。
2. 目标仓库的 `git worktree list`：确认工作树数量与各自分支。
3. 项目根 `AGENTS.md` 或项目规则里若已约定任务分类清单，直接用作方面名，不自己另拟。
4. 仓库位置、路径与姓名以机器档案为准，不要凭记忆猜；档案缺某个路径键就跳过该类来源并在输出里说明。

## 默认范围

- 仓库：当前 git 仓库，加上它的全部工作树（含未提交改动）。
- 时间：最近 7 天；输出开头注明实际取数区间。
- 作者：机器档案"我的名字"的提交，他人提交与他人署名的文档默认整节删掉。
- 作者名核对：先跑 `git log --all --since=<日期> --pretty='%an|%ae' | sort -u`，档案值与实际作者名或邮箱对不上时报告并等用户确认，不静默放宽成全部作者。
- 文档来源：只取与当前梳理范围相关的文档。梳理单仓库时，用仓库名、项目名与该区间日期在"工作计划总结""桌面交付"内筛；档案里没有对应目录时如实说明，不扩大取材面。

## 可调整范围

- 时间：用户给了"自某天以来 / 本周 / 上个月 / 具体区间"就按给的，换算成绝对日期传给 `--since`、`--until`。
- 仓库：用户要求跨项目时，按机器档案"项目父级"或"项目清单"逐仓库汇总，每个仓库单独分节并在开头标仓库名。
- 全量梳理：用户要求"梳理全部工作/所有项目"时，机器档案里已记录的工作路径全部纳入——各 git 仓库加"工作计划总结""桌面交付""工作参考资料""全局工作台"的 todo 与 notes，逐类取区间内容。
- 分支：用户点名某分支或某工作树时只取该 ref；未提交改动始终单列。
- 作者：用户明确要"也算某某的"才纳入他人，并单独成节标明是谁。

## git 取数步骤

1. `git worktree list` 列出全部工作树与所在分支。
2. `git log --all --since=<日期> --no-merges --date=short --pretty=format:'%ad|%an|%s'`：工作树共用同一对象库，一次 `--all` 即覆盖所有本地与远端 ref。
3. 按 `%s` 去重：同一条消息在多个分支重复出现（cherry-pick、同步主干）时只保留一条，日期取最早那次。
4. 按作者过滤出"我的名字"；`--all` 带进来的远端分支上他人同步提交在这一步被剔除。
5. 逐工作树 `git status --porcelain`，必要时补 `git diff --stat`；有未提交项时在对应日期加一条并标"进行中"，不标合入状态。
6. 判定方面：优先用项目规则里的分类清单，没有清单时按提交实际改动的项目目录或模块动态归纳，不套固定分类表。

## 非 git 来源与交叉比对

- 取材：`工作计划总结` 下的月度计划与月报、待办排期、按项目分目录的日记录（形如 `YYYY-M-D.md`）；`桌面交付` 下区间内新增或修改的 md、txt、docx、xlsx 留档、手册与排查记录。全程只读，不在这些目录写文件或改文件名。
- 日期双口径：优先文件名日期（`_20261104`、`2026-11-4.md`），文件名没有再取 mtime；两者都缺或互相矛盾时不猜，归入"日期未确认"并在对账里列出。
- 署名核对：文档正文或文件名含他人署名、或明显是他人产出时不计入，需要时先问用户。
- 比对三类事实，都只陈述不推断：
  1. 文档有、git 无：非代码工作（调研、现场排查、手册与方案编写、文档交付），并入对应日期条目，不因没有提交而漏掉。
  2. git 有、文档无：不逐条标注，只在末尾对账里给一句覆盖度统计（区间内有提交的工作日数、其中有留档的天数）。
  3. 时间与内容矛盾：文档日期与提交日期错位、日记录在某日后停更而提交仍在推进、留档标题与提交主旨不符——逐条列出事实，不猜原因。
- 去重：同一事项的留档文档与实现提交合成一条，不重复计数；只有文档内容超出提交范围（额外结论、现场验证、后续待办）才另起一条。

## 交付格式

- 整份内容放进一个 markdown 围栏代码块，方便直接复制粘贴。
- 顶层标题带区间与归属，例如 `# 10.29–11.04 我的工作记录`。
- 按日期分节：`## 10.29`。
- 节内按方面分组，方面名作小标题：`**设计器**`。
- 同一方面的各项工作逐条列出，一项一行、一句话描述，不揉成一段。
- 行内不再重复方面前缀，分组已由小标题表达。
- 一句话里可用括号或分号补足关键对象与效果，但不展开过程叙述。
- 主结构后加一节 `## 对账`：写覆盖度统计、矛盾与停更事实、日期未确认的文档清单；没有差异时写"无差异"，不编造。

## 禁止

- 不标注是否并入主干、不写分支归属与合入状态；梳理目的是记录干了什么，不是跟踪合入。
- 不写测试通过数、诊断叙述、批次推进过程这类会话内细节。
- 不按提交标题原样罗列，要压成能读懂的一句话；也不要为凑篇幅把一条扩成多句。
- 默认不含他人提交与他人署名文档。
- 不从文档日期倒推提交内容，也不把计划里的待办当成已完成工作计入。
- 内容要贴给别人看时先确认外发范围：外发版本去掉他人内容、本机路径与未定稿文档。

## 验证

- 日期是否连续覆盖区间内有提交或有留档的每一天，工作树内未提交项是否已补入。
- 每个方面小标题下是否一事项一行，是否残留合入状态、他人内容或过程叙述。
- 条目总数与去重后按作者过滤的提交数量级相当（文档项与未提交项另计）；明显偏少说明漏了工作树、ref 或文档目录，回头补取。
- `## 对账` 是否给出覆盖度与差异事实；列出的差异条数与正文条目能对上。
